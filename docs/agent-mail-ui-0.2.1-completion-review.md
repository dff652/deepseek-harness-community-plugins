## 具体发现与修复任务

- [ ] **C01 / A1–A2：投递标签与色彩不得借用任务结果。**
  `view.js` 的 `sentItems` 将 provider 派生 `status` 存为 `deliveryStatus`，保留真实投递值于 `rawDeliveryStatus`。
  `client-src.js` 的详情却将 `deliveryStatusLabel(selected.deliveryStatus)` 标为“投递”，
  颜色和图标还来自可能返回 task 层的 `mailRowStatus(selected, 'sent')`。
  合成 `status=completed, delivery_status=acked, task_status=completed` 显示“投递：已完成”，而原始投递是“已确认收悉”。
  保持列表任务汇总，但详情投递使用真实投递字段和对应色彩；加真实 provider payload 形状的正负回归。
- [ ] **C02 / A4：错误呈现边界未完成。**
  `sanitizePublicError` 的当前正则未覆盖 URL 内凭据、较短敏感值及非 home 类路径。
  宿主 `index.js` 的 API catch 也将异常原文返回 JSON；这是既有边界问题，本轮未修复，客户端净化不能替代服务端处理。
  需按可信错误码提供用户文案、追踪输入来源并在正确边界净化；不能只不断叠加正则或以隐藏 UI 当 API 安全修复。
  验收覆盖主错误、发送、详情、工具卡片和管理适配来源，避免把测试输入或真实凭据写入公开材料。
  管理适配已有安全错误映射，不能仅因组件直接渲染字符串就认定其来源不安全；必须逐条追踪。
- [ ] **C03 / A3：能力摘要仍把缺失归因写死。**
  `recipientCapabilitySummary` 只要设备字段缺失就称“没有可信设备登记和心跳”，不能区分不支持、未配置、失败或过期。
  所有字段都有值时，外层反而回退“当前没有额外设备信息”。
  按已知能力/证据呈现，未知原因不臆测；不引入 B1 的真实采集范围。
- [ ] **C04 / A6：恢复原始浏览器验收门槛。**
  补齐真实 better-sidebar、设置入口、主题切换、键盘/焦点、error/ack、关闭重开、隔离 DSH 重启、超时未知结果与刷新失败。
  profile 安装/卸载测试不等于带邮件状态的服务重启验证；只证明隐藏页停轮询不等于卸载清理。
- [ ] **C05 / A4–A6：隔离管理生命周期未验收。**
  创建独立管理宿主/合成凭据，验证未配置、未认证、配对过期、保存待激活、取消、恢复和激活。
  缺少现成夹具不是通过理由；不得为补验使用生产或用户预览。
- [ ] **C06 / A6–A7：精确归档证据重新闭环。**
  找出两个摘要差异来源，记录 source commit、版本、打包文件、摘要与运行时；以最终包重新跑干净安装及 receipts/browser 门。
  未完成前保留两条摘要及各自证据范围，不能仅用新摘要覆盖旧记录后宣布已验收。
- [ ] **C07 / A5：仓库首页仍有旧版表达。**
  包 README 和 description 已更新，但根 README 仍有旧版徽标、“now live”旧生产基线及旧工具数量/包结构说明。
  包 README 还将已发布 provider alpha.7 称为 unreleased；一并核对。
  将历史说明与当前候选/发布/部署分开，检查市场文案来源；外部市场改造仍为 B3。
- [ ] **C08 / A6–A7：完成状态与实际证据对齐。**
  原清单把 A6/A7 和多项缩减后的验收打勾，却列有明确未跑项。恢复未完成状态并逐项补证据，
  由主代理审查完整差异后决定最终通过。不能以“已列出限制”代替原本要求的验收。
